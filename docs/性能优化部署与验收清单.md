# 小程序性能优化部署与验收清单

本文档用于把本次代码改造安全地发布到测试云环境，再分阶段切换正式环境。仓库中的代码已经保留旧读取路径；数据库索引、环境变量、云函数部署和正式图片回填仍需在对应云环境中执行。

## 1. 发布前基线

在同一构建版本、同一测试账号下记录以下数据，每个组合至少运行 5 次，取中位数并记录 P75。

| 操作路径 | 次数 | 图片请求数 | 传输字节 | CDN 流量 | 备注 |
| --- | ---: | ---: | ---: | ---: | --- |
| 首页冷启动 | 5 |  |  |  | 同一手机、同一网络 |
| 分类首屏 | 5 |  |  |  | 清缓存后测试 |
| 打开五图案例 | 5 |  |  |  | 初次应仅 1 张展示图 |
| 滑动到第二张 | 5 |  |  |  | 此时才请求第二张展示图 |
| 下载当前图片 | 5 |  |  |  | 应保存 1600px 展示图 |

开发者工具需要打开自动审计。上传体验版后，再从“小程序助手”记录正式链路的首屏 P75、云函数错误率和图片失败率。

发布前另外完成：

- 导出 `wine_packaging` 和 `home_banners`；
- 记录 `catalog_meta/current`；
- 保留当前可发布的小程序版本；
- 不修改静态托管安全开关、缓存 TTL 和云存储权限。

## 2. 测试云环境准备

### 2.1 数据库索引

在测试环境确认或新建以下索引：

- `wine_packaging`
  - `caseId`
  - `isVisible + sortOrder`
  - `isVisible + homeSections.values + sortOrder`
- `home_banners`
  - `isVisible + sortOrder`
- `favorites`
  - `_openid + createdAt`
  - `_openid + caseDocId`
  - `_openid + caseId`
- `browse_history`
  - `_openid + lastViewedAt`
  - `_openid + caseDocId`
  - `_openid + caseId`
  - `_id + _openid`（客户端按文档 ID 更新或删除时的创建者权限校验）
- `user_profiles`
  - `openid`

创建集合 `catalog_meta`，并创建文档：

```json
{
  "_id": "current",
  "revision": 1
}
```

不要删除现有索引、旧图片字段或用户数据。案例管理云函数在案例新增、编辑、显隐和删除后会递增此版本。

### 2.2 云函数环境变量

`caseAdmin` 和 `imageProcessor`：

```text
CASE_ADMIN_OPENIDS=案例管理员openid1,案例管理员openid2
ADMIN_OPENIDS=兼容的管理员openid列表
```

`userData`：

```text
ADMIN_OPENIDS=兼容的管理员openid列表
INQUIRY_ADMIN_OPENIDS=需求管理员openid列表
CASE_ADMIN_OPENIDS=案例管理员openid列表
NOTIFICATION_ADMIN_OPENIDS=通知管理员openid列表
```

对应的 `inquiryAdmin`、`caseAdmin`、`imageProcessor` 和 `notificationAdmin` 云函数也应设置同名专用变量。专用变量未设置、为空或只有空格时会回退到 `ADMIN_OPENIDS`；一旦设置专用列表，通用管理员不会自动获得该角色。前端角色信息仅控制入口显示，后台云函数仍独立鉴权。

`contactAdmin` 优先使用 `CONTACT_ADMIN_OPENIDS`，同样回退到 `ADMIN_OPENIDS`。`notificationDispatcher` 继续使用 `ADMIN_OPENIDS` 用于人工补偿调用，定时触发不依赖客户端角色。

## 3. 云函数部署顺序

本轮兼容版本严格按以下顺序部署：

1. `imageProcessor`
2. `caseAdmin`
3. `caseCatalog`

可使用微信开发者工具上传，也可在开发者工具生成的脚本上下文中运行 `miniprogram/uploadCloudFunction.sh`。部署后先直接调用：

- `imageProcessor.healthCheck`
- 使用一张测试图调用 `imageProcessor.generateCaseVariants`
- 确认返回 `displayFileID`、`thumbnailFileID`、`bannerFileID` 和 `variantVersion: 2`
- `caseCatalog.getHomeFeed`
- `caseCatalog.getCatalogSnapshot`
- `caseCatalog.getCaseDetail`
- `caseCatalog.listUserLibrary`

缩略图应不超过约 100KB，Banner 应不超过约 180KB，原图仍保留。检查所有失败响应均为 `{ok:false, code, message}`，隐藏案例不返回，公共详情与公共图片 URL 接口不签发原图临时地址。

## 4. 图片回填

先安装根目录依赖并仅预览 5 条：

```bash
npm install
npm run backfill:image-variants:dry
```

默认使用新的断点文件 `.case-variant-v2-backfill.json`。确认待处理记录后执行首批 5 条：

```bash
node scripts/backfill-case-image-variants.mjs \
  --limit 5 \
  --checkpoint .case-variant-v2-backfill.json
```

在详情页和下载流程分别检查：

- 缩略图裁切主体是否正确；
- 缩略图是否不超过 100KB；
- 展示图最长边是否不超过 1600px；
- Banner 最长边是否不超过 1080px、大小是否不超过约 180KB；
- 下载是否得到展示图而非原图；
- 五图详情初次是否仅请求 1 张展示图；
- 滑动第二张后是否才请求第二张展示图；
- 图片处理失败时是否禁止保存并显示“重试处理”；
- 旧字段案例和新字段案例能否混合显示。

数据库抽查应满足：

- `imageVariantVersion === 2`
- `galleryImages`、`sourceGalleryImages`、`galleryThumbnails`、`galleryBanners` 数量一致
- `coverThumbnail === galleryThumbnails[0]`
- `coverBanner === galleryBanners[0]`
- 同一位置的原图、展示图和缩略图文件 ID 不相同
- 独立 `home_banners` 记录存在 `optimizedImage` 和 `imageVariantVersion: 2`

确认后继续：

```bash
npm run backfill:image-variants
```

脚本以 5 条为一个进度批次，只跳过已经成功的记录，失败项会在下次 `--resume` 时重试；单个案例全部变体上传成功后才更新数据库。案例与独立 Banner 全部成功时才将 `catalog_meta.current.revision` 递增一次。完成后再次运行 `--dry-run`，要求案例和独立 Banner 待处理数均为 0。不要在正式版稳定至少 7 天前删除原图、旧字段或旧读取路径。

## 5. 客户端分阶段发布

1. 发布包含新聚合接口和旧路径回退的体验版，验证首页、分类、详情、收藏、历史。
2. 完成 5 条图片试跑，验证通过后再从断点回填全部历史案例与独立 Banner。
3. 清除测试设备缓存并重新冷启动验收。
4. 发布正式版，连续观察 3 个具有可比访问量的自然日。
5. 原图和旧字段至少保留 7 天，文件清理另行安排。

每阶段单独留存上一个可发布版本。若新接口错误率超过 1%，或同设备同网络下首屏没有改善，回滚当前阶段客户端，保留云端数据和原图，排查冷启动、索引和图片变体。

## 6. 验收项目

- 首页数据仅 1 次 `caseCatalog` 调用；首页最多 5 个轮播、4 个热门、6 个最新。
- 分类首次仅 1 次目录调用；本地筛选不重新请求快照。
- 收藏最多 100 条、历史最多 50 条；案例查询按 10 个 ID 分批且并发不超过 4。
- 20 分钟内带 `knownRevision` 校验；命中时返回 `notModified`。
- 下拉刷新不使用本地或内存缓存。
- 分类页 `data` 中没有全量案例，首次最多 12 张；加载更多每次只追加 12 张路径数据。
- 详情首次只有第一张使用展示图，其他项先使用缩略图；滑动或点击时只升级目标项。
- 图片预览和“下载图片”均使用 1600px 展示图，不请求原图。
- 首页最多 5 个轮播且保留自动轮播；优先使用 `optimizedImage` 或 `coverBanner`。
- 所有列表继续优先使用缩略图。
- 图片处理任一步骤失败时表单与案例数据保持原样，保存按钮不可用，可直接重试。
- 管理端清理接口删除前会再次检查案例、图库和独立 Banner 引用。
- 单卡图片失败只更新对应卡片。
- 个人中心只调用一次 `getSessionSummary`，资料编辑返回后缓存失效。
- 主包只包含首页、分类、个人中心和详情；后台分包不预下载。
- 开发者工具确认主包小于 350KB，并与改造前记录比较至少减少 90KB。
- `npm test` 全部通过。

上线目标：

- 云函数错误率低于 1%；
- 图片加载失败率低于 0.5%；
- 同路径详情首屏展示图请求数从最多 5 个降为 1 个；
- 平均每次下载达到 80～120KB；
- 约 10,000 次下载对应 CDN 不高于约 1.2GB；
- 连续 3 个可比自然日 CDN 流量至少下降 35%。

若仍高于约 1GB/天，先查看 CloudBase 高流量文件或 URL 排行，判断是否集中在展示图、Banner、原图或少数案例，再决定是否评估套餐升级。

## 7. 本地安全说明

根依赖安装当前会报告第三方依赖审计告警。不要直接运行带破坏性升级的自动修复；应先查看依赖链、在测试环境升级并重新执行全部测试，再决定是否更新锁定版本。
