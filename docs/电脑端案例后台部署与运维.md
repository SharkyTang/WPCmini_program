# 电脑端案例后台：CloudBase 部署、迁移与回滚

本文用于把 `admin-web`、`caseAdmin`、`imageProcessor` 和兼容版 `caseCatalog` 先发布到独立 staging，再切换正式环境。所有命令都必须显式传入环境 ID；仓库不保存正式环境 ID、腾讯云 Secret、管理员密码或 OpenAI Key。

## 1. 环境与安全基线

### 1.1 本地环境

项目固定使用 Node.js 22 LTS：

```bash
nvm use
npm ci
npm test
```

复制 `.env.example` 为 `.env.local`，只在本机填写：

```text
CLOUDBASE_ENV_ID=<当前操作的环境 ID>
TENCENTCLOUD_SECRET_ID=<仅服务端脚本使用>
TENCENTCLOUD_SECRET_KEY=<仅服务端脚本使用>
```

`VITE_*` 会进入浏览器构建产物，只能包含环境 ID、区域和 Publishable Key。任何 Secret、管理员密码、OpenAI Key 都不得使用 `VITE_` 前缀。提交前运行 `git status --short`，确认 `.env.local` 未进入版本控制。

根目录 `server.mjs` 继续只服务本地图片分类工具，它会暴露仓库文件，禁止把它作为后台服务器部署或暴露到公网；公网后台只发布 `admin-web/dist` 静态产物，并通过受保护云函数访问数据。

### 1.2 环境隔离

在 CloudBase 控制台新建独立 staging 环境，并分别记录：

| 配置 | staging | production |
| --- | --- | --- |
| 环境 ID | 人工填写 | 人工填写 |
| Publishable Key | 人工填写 | 人工填写 |
| 管理员 UID | 测试账号 UID | 正式账号 UID |
| 默认托管域名 | staging 域名 | 正式域名 |

不要让 staging 前端指向正式函数、数据库或存储。构建前检查 `VITE_CLOUDBASE_ENV_ID`，迁移和备份前检查命令里的 `--env`。

### 1.3 身份认证

在「身份认证 → 登录方式」中启用用户名/密码，关闭匿名登录和公开注册。由控制台预先创建管理员并记录其 CloudBase UID；路由守卫以 `auth.getSession()` 的真实 session 为准。Web SDK v3 的密码登录不会代替控制台创建账号，禁止把“找不到账号”自动降级为注册流程。

将管理员分别加入两个云函数的环境变量：

```text
CASE_ADMIN_UIDS=uid-a,uid-b
ADMIN_OPENIDS=原有小程序管理员openid-a,openid-b
ADMIN_WEB_WRITE_ENABLED=false
```

先保持 `ADMIN_WEB_WRITE_ENABLED=false`。环境变量在 CloudBase 控制台的函数配置中维护，不写入代码或 `cloudbaserc.json`。CloudBase 官方说明：[Web SDK v3 认证](https://docs.cloudbase.net/api-reference/webv3/authentication)、[云函数环境变量](https://docs.cloudbase.net/cloud-function/function-configuration/env)。

### 1.4 数据库与存储权限

桌面后台不直接读写 `wine_packaging`、`catalog_meta` 或 `home_banners`，全部经过受保护云函数。因此这些集合必须继续拒绝客户端写入。当前小程序仍保留 `cloudData.js` 直读作为 `caseCatalog` 故障时的兼容降级路径，本版本应**保留并复核现有读取规则，仅禁止客户端写入**，不能把正式环境的集合读取权限直接改成 `false`。

只有未来确认所有小程序版本都已移除直读降级、且已完成回归和灰度后，才可另行评估：

```json
{
  "read": false,
  "write": false
}
```

不要批量替换其他用户数据集合的规则。CloudBase 的 Web 身份字段是 `auth.uid`，微信小程序身份字段是 `auth.openid`，详见[数据库安全规则](https://docs.cloudbase.net/database/security-rules)。

下面是**开启 Web 写入阶段**使用的规则模板。只读冒烟期间先不要发布这条 Web 上传规则，应保持 `wine-packaging/admin-web/` 对浏览器拒绝写入；`ADMIN_WEB_WRITE_ENABLED` 是云函数开关，不能拦截浏览器直接调用 Storage SDK。把真实 UID 写入控制台规则，并保留现有业务所需的读取规则：

```json
{
  "read": "<保留并复核现有读取规则>",
  "write": "auth != null && auth.loginType != 'ANONYMOUS' && (((auth.uid == 'uid-a') && (/^wine-packaging\\/admin-web\\/uid-a\\//.test(resource.path) == true)) || ((auth.uid == 'uid-b') && (/^wine-packaging\\/admin-web\\/uid-b\\//.test(resource.path) == true))) && ((/\\.jpg$/.test(resource.path) == true) || (/\\.jpeg$/.test(resource.path) == true) || (/\\.png$/.test(resource.path) == true) || (/\\.webp$/.test(resource.path) == true))"
}
```

每位管理员都要使用 `auth.uid` 与路径段显式绑定的独立分支；若 UID 含需 URL 编码的字符，路径分支应填写前端实际生成的编码后值。不能只校验 UID 白名单和公共 `admin-web/` 前缀，否则管理员 A 可以覆盖管理员 B 的上传文件。

规则生效后分别验证：未登录上传失败、非管理员上传失败、管理员只能把 JPEG/PNG/WebP 上传到 `wine-packaging/admin-web/{自己的 uid}/{batchId}/`，并确认管理员 A 写入 `uid-b` 路径会失败。20MB 单图上限、UID 与路径一致性还会由云函数再次校验。修改存储规则可能有 1–3 分钟延迟，语法参见[云存储安全规则](https://docs.cloudbase.net/storage/security-rules)。

## 2. Staging 初始化与迁移

### 2.1 资源和索引

在 staging 创建或导入 `wine_packaging`、`home_banners`、`catalog_meta`，并确保 `catalog_meta/current` 至少有：

```json
{
  "_id": "current",
  "revision": 1
}
```

Web 批量上传会在同一 `catalog_meta` 集合写入
`upload_batch_<sha256(actorId:uploadBatchId)>` 内部声明文档。它与案例、连续编号和
`catalog_meta/current` 在同一事务提交，用于保证同一上传批次只递增一次目录
`revision`；不要在仍可能重试上传任务时手工删除这些声明。备份与恢复脚本会连同
`catalog_meta` 一并保存、校验和恢复这些文档。

保留现有索引，再为后台查询补齐：

- `wine_packaging`: `caseId` 唯一索引；`deletedAt + sortOrder + caseId`；`deletedAt + isVisible + sortOrder + caseId`。
- 若控制台支持数组字段组合索引，再按实际慢查询为 `packageTypes.values`、`styles.values`、`scenes.values`、`statuses.values`、`homeSections.values` 分别建立索引；不要一次建立互相冲突的多数组复合索引。
- `home_banners`: `isVisible + sortOrder`。

### 2.2 部署兼容云函数

先登录 CloudBase CLI，然后按依赖顺序部署。也可使用微信开发者工具逐个上传并安装依赖。

```bash
npm install -g @cloudbase/cli
tcb login

tcb fn deploy imageProcessor --dir miniprogram/cloudfunctions/imageProcessor -e <staging-env-id> --force
tcb fn deploy caseAdmin --dir miniprogram/cloudfunctions/caseAdmin -e <staging-env-id> --force
tcb fn deploy caseCatalog --dir miniprogram/cloudfunctions/caseCatalog -e <staging-env-id> --force
```

部署后确认函数环境变量仍存在；旧版 CLI 可能覆盖线上变量，执行前先看 `tcb fn --help`。官方命令参考：[部署云函数](https://docs.cloudbase.net/cli-v1/functions/deploy)。

### 2.3 备份、预演与迁移

先生成逻辑备份：

```bash
npm run backup:cloudbase -- --env <staging-env-id>
npm run backup:verify -- backups/cloudbase-<staging-env-id>-<timestamp>
```

备份目录包含三个集合 JSON、每个文件的 SHA-256、`catalog_meta/current` 快照和 `storage-files.json`。后者是数据库引用的 `cloud://` 文件清单，不包含文件二进制副本；需要删除或搬迁云文件前必须另做对象存储副本。

只读预演：

```bash
npm run migrate:admin:dry -- --env <staging-env-id>
```

核对总案例数、待更新数、三个首页区域计数和 `nextCaseNumber`。迁移规则固定为：

- 缺失或非法的 `version` 补为 `1`，已有正整数版本不回退。
- 只为当前 `isVisible === true`、未删除且属于对应首页区域的案例生成顺序。
- `banner`、`popular` 按旧 `sortOrder` 升序，`latest` 按旧 `sortOrder` 降序；容量分别为 5、4、6。
- 隐藏、删除、超出首页容量的案例不占首页顺序；重复或越界顺序按旧实际展示顺序修复。
- `nextCaseNumber` 取 `case_1` 至 `case_999999` 中最大规范编号加一；时间戳式编号不参与计算，并且不会降低已预留的值。

确认预览后执行：

```bash
npm run migrate:admin -- --env <staging-env-id>
npm run migrate:admin:dry -- --env <staging-env-id>
```

第二次预演应显示待更新案例为 0。迁移逐条幂等写入，全部案例完成后才更新 `catalog_meta/current.nextCaseNumber`、`updatedAt` 并把 `revision` 递增一次；若中途断开，保持写入开关关闭，直接重新运行即可。

## 3. 构建、托管与验收

为 staging 创建 `admin-web/.env.staging.local`，只写入对应的三个 `VITE_*` 公共配置，然后：

```bash
npm --prefix admin-web ci
npm --prefix admin-web run typecheck
npm --prefix admin-web test
npm --prefix admin-web run build -- --mode staging
tcb hosting deploy admin-web/dist / -e <staging-env-id>
```

`--mode staging` 不可省略：Vite 只有在该模式下才会读取 `.env.staging.local`。构建后先检查产物确实包含 staging 环境标识，再执行托管部署。

后台使用 hash 路由以兼容 CloudBase 默认静态托管域名，入口分别为
`/#/login`、`/#/cases`、`/#/cases/upload`、`/#/homepage` 和 `/#/trash`。
不要配置“404/4xx → index.html”重定向规则；该规则在部分默认域名上会递归命中自身并产生
`STATIC_RESOURCE_TOO_MANY_REDIRECTS`。默认首页保持 `index.html` 即可。为兼容已保存的旧地址，
构建产物同时提供 `/case/` 与 `/cases/` 两个静态入口，它们只负责跳转到 `/#/cases`。

先在 `ADMIN_WEB_WRITE_ENABLED=false` 且 Web 上传规则未开放时，验收登录、退出、路由守卫、列表、准确总数、350 条分页、筛选和临时图片 URL。随后仅在 staging 开启两个云函数写入并发布 UID 与路径绑定的存储规则，再完成：

1. 单图生成隐藏案例，多图合并为最多 9 图案例。
2. 三并发上传、单项失败重试，同一 `clientMutationId` 不重复创建；在等待或处理中强制刷新后，IndexedDB 中的原文件、`uploadBatchId` 和任务号仍可恢复并安全重试。
3. 编辑保存、故意制造 `expectedVersion` 冲突、刷新后重新提交。
4. 最多 50 条追加/移除/替换标签及上下架、置顶；价位是单值字段，追加只补空值、移除只清除匹配值、替换可覆盖或清空。
5. 全局排序和三个首页区域排序，刷新后顺序不变且容量正确。
6. 移入回收站立即下架；恢复后保持隐藏。
7. 小程序首页、分类、详情和手机案例管理回归；运行根目录完整 `npm test`。

## 4. 正式发布

1. 记录当前静态站版本、三个云函数版本和函数环境变量，完成正式备份并执行 `backup:verify`。
2. 部署兼容云函数，保持 `ADMIN_WEB_WRITE_ENABLED=false`；用小程序完成首页、分类、详情冒烟。
3. 对正式数据执行迁移 dry-run，人工保存输出；确认后执行迁移，再 dry-run 验证 0 待更新。
4. 把 production 的三个 `VITE_*` 写入 `admin-web/.env.production.local`，执行 `npm --prefix admin-web run build -- --mode production`；确认产物连接正式环境且不存在 `TENCENTCLOUD_SECRET`、管理员密码或 OpenAI Key 后，再部署静态站。
5. 在控制台预建正式管理员并把 UID 加入 `CASE_ADMIN_UIDS`；先准备好绑定该 UID 的存储规则，但只读冒烟期间不要发布 Web 上传权限。
6. 只读冒烟通过后，把两个写函数的 `ADMIN_WEB_WRITE_ENABLED` 改为 `true`，随即发布 UID 与路径绑定的存储规则；确认非管理员、跨 UID 路径和非图片扩展名仍被拒绝。
7. 用专门的隐藏测试案例完成新增、编辑、上下架、首页编排、回收站恢复；验收后删除其首页归属并保持隐藏。

上线后至少观察一个完整工作日：`UNAUTHENTICATED`/`FORBIDDEN` 分布、云函数 5xx、版本冲突、上传失败与重试、目录 revision、小程序图片加载错误。服务故障不得被前端归类为“无权限”。

## 5. 备份恢复演练

恢复演练只在空的 staging 环境进行：

1. 对备份运行 `npm run backup:verify -- <directory>`；任何数量或 SHA-256 不一致都停止。
2. 在 staging 预先创建空的 `wine_packaging`、`home_banners`、`catalog_meta` 集合，先执行：

   ```bash
   npm run restore:cloudbase:dry -- \
     --source <backup-directory> \
     --env <empty-staging-env-id>
   ```

3. 只有预览显示目标集合全部为 0 且“允许写入：是”时，才执行双重确认的恢复：

   ```bash
   npm run restore:cloudbase -- \
     --source <backup-directory> \
     --env <empty-staging-env-id> \
     --confirm-env <empty-staging-env-id>
   ```

   脚本不删除、不覆盖、不合并；任一目标集合非空会拒绝写入。中途失败时应清空这次专用的 staging 集合并从头演练，不要把 `--apply` 改成覆盖模式。

4. 核对恢复后的 `catalog_meta/current.revision` 和 `nextCaseNumber`。
5. 逐条核对 `storage-files.json` 的文件 ID 是否仍可签发临时 URL；清单不含二进制，缺失文件必须从对象存储副本恢复。
6. 比较恢复后集合记录数与 `manifest.json`，运行迁移 dry-run，最后执行后台与小程序只读冒烟。
7. 记录演练日期、备份目录、恢复环境、操作者、记录数、缺失云文件数和验收结果。

正式环境只有在确认数据损坏且负责人批准后才恢复。恢复前再次备份当前故障现场，关闭 Web 写入，并停止其他人工编辑；不要为了代码回滚而回滚数据库。

## 6. 回滚

优先执行兼容回滚，数据和图片默认保留：

1. 立即把 `caseAdmin`、`imageProcessor` 的 `ADMIN_WEB_WRITE_ENABLED=false`，并撤回 `wine-packaging/admin-web/` 的浏览器写入规则；两项必须作为同一次关闭写入操作，不能只依赖云函数开关。
2. 若仅前端故障，重新部署上一个已验收的 `admin-web/dist`；不要删除新案例。
3. 若函数故障，按 `caseCatalog`、`caseAdmin`、`imageProcessor` 的逆序恢复上一个版本，然后回归小程序。
4. `version`、`homeSectionOrder`、回收站字段和 `nextCaseNumber` 对旧客户端是附加字段，代码回滚时保留。
5. 只有校验确认数据库损坏时，才按已演练流程恢复集合；恢复后把 `catalog_meta/current.revision` 递增，迫使客户端刷新。
6. 云文件先保留，不执行批量删除。待问题关闭并经过保留期后，再根据引用清单单独清理。

回滚结束后记录触发时间、影响范围、关闭写入时间、恢复版本、数据是否恢复及最终校验结果。
