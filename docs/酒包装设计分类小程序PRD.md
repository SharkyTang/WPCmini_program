# 酒包装设计分类小程序 PRD

文档日期：2026-06-16  
产品阶段：v0 数据准备工具已实现；v1 微信小程序待产品化开发  
项目定位：先服务自家私人定制酒包装设计店，验证案例展示和筛选效率，再考虑扩展给更多商家。

## 1. 背景和问题

私人定制酒包装设计店积累了大量案例图片，但这些图片通常散落在朋友圈、聊天记录或本地文件夹里。客户想找参考图时，商家需要反复翻找、截图、解释风格，沟通成本高，也容易让客户表达不清楚自己的设计方向。

本项目要解决的核心问题不是先做一个完整平台，而是先把已有酒包装案例结构化，让客户可以更快看到、筛选和表达参考方向。

当前项目已经拆成两部分：

- 本地图片分类工具：用于把本地案例图片整理成小程序可导入的数据。
- 微信小程序：用于面向客户展示案例图，并支持按分类筛选。

## 2. 产品目标

### 2.1 v1 目标

让客户在微信小程序里快速浏览自家酒包装案例，并通过分类筛选找到接近自己需求的参考图。

### 2.2 业务目标

- 减少商家在前期沟通中反复找图的时间。
- 帮助客户用案例图表达“想要什么风格、什么包装内容、什么使用场景”。
- 把第一批 89 张案例图整理成可持续维护的数据资产。

### 2.3 非目标

v1 不追求完整 SaaS 平台，不做多商家、不做商家手机端上传、不做 AI 自动分类、不做在线生成设计图、不做成交转化统计。

## 3. 用户角色

### 3.1 客户

可能正在准备定制白酒包装，需要参考礼盒、瓶标、瓶子、手提袋、外箱等案例。客户通常不会用专业设计术语描述需求，更依赖“我喜欢这个风格”“这个盒型可以参考”。

### 3.2 商家/设计顾问

需要快速给客户展示案例，减少翻朋友圈、翻文件夹、临时截图的成本。希望客户先自行筛选，再带着参考方向进入沟通。

### 3.3 数据整理者

负责用本地分类工具标注案例、导出图片和 `cases.json`，再把图片上传到微信云存储，并把案例数据导入云数据库。

## 4. 当前项目状态

### 4.1 已完成：本地图片分类工具

本地工具已经具备以下能力：

- 支持选择本地图片文件夹或多选图片。
- 支持 `.jpg`、`.jpeg`、`.png`。
- 按稳定顺序排序并生成 `case_001`、`case_002` 等编号。
- 原图不重命名、不覆盖、不删除。
- 手动选择酒类、包装内容、风格、价位感、工艺、使用场景、状态。
- 只有“酒类”和“包装内容”为必填。
- 标题、备注、风格、价位感、工艺、场景、状态为可选。
- 浏览器本地保存标注进度。
- 导出压缩后的 JPG 图片和 `cases.json`。
- PNG 透明区域导出为白底 JPG。
- 图片最长边压缩到 1600px，JPG 质量为 0.85。
- 导出记录保留 `imageFileID` 字段，等待微信云存储上传后回填。

### 4.2 当前限制

- 本地工具不负责上传微信云存储。
- 本地工具不负责导入云数据库。
- 本地工具不是商家后台，也不做登录权限。
- 微信小程序目录当前仍是云开发 quickstart 骨架，尚未替换成案例展示产品页面。
- 小程序 `env` 仍为空，需要配置真实云开发环境。

## 5. 信息架构

v1 小程序只保留面向客户的核心路径：

```text
首页 / 案例列表
  - 顶部品牌和说明
  - 分类筛选
  - 案例图片网格
  - 空状态 / 加载状态 / 错误状态
```

v1 暂不单独建设复杂详情页和收藏夹。客户可以先在列表中完成浏览和筛选，后续版本再加入详情、收藏、参考图组合和需求描述生成。

## 6. v1 功能需求

### 6.1 案例列表

客户打开小程序后，应直接看到案例图片列表。

要求：

- 默认展示所有 `isVisible = true` 的案例。
- 按 `sortOrder` 升序展示。
- 案例卡片至少展示图片、标题或编号、核心标签。
- 如果标题为空，可展示编号或主要分类，例如“白酒 · 礼盒”。
- 图片来自微信云存储 fileID。
- 图片加载失败时显示占位状态，不能让页面塌陷。

验收标准：

- 导入 89 条案例数据后，首页可以完整加载可见案例。
- 无筛选条件时，案例顺序与 `sortOrder` 一致。
- `isVisible = false` 的案例不展示。

### 6.2 分类筛选

客户可以按分类缩小案例范围。

v1 必须支持的筛选：

- 包装内容：整套包装、瓶标、瓶子、礼盒、桶盒、卡盒、手提袋、外箱。
- 风格：高端、国潮、新中式、复古、简约、商务、时尚、喜庆。
- 使用场景：婚宴、送礼、商务招待、节庆礼赠、商超陈列、电商展示、企业纪念。

v1 可展示但不必须作为首屏重点的筛选：

- 价位感：低端、中端、高端、奢华。
- 工艺：烫金、浮雕、镭射、特种纸、哑膜。
- 状态：推荐、热门、新上传。

交互要求：

- 筛选项支持点选和取消。
- 多选字段采用“包含任一标签”的逻辑。
- 单选字段同一时间只保留一个值。
- 提供“清空筛选”入口。
- 筛选后没有结果时，展示空状态，而不是空白页面。

验收标准：

- 选择“礼盒”后，只展示 `packageTypes` 包含“礼盒”的案例。
- 同时选择多个包装内容时，展示匹配任一包装内容的案例。
- 清空筛选后恢复全部可见案例。

### 6.3 数据读取

小程序从微信云数据库读取案例集合。

要求：

- 数据集合建议命名为 `cases`。
- 首次加载读取可见案例。
- 需要处理加载中、加载失败、空数据三种状态。
- 读取失败时给出用户能理解的提示，不暴露技术错误。

验收标准：

- 云开发环境配置正确后，小程序可以读取 `cases` 集合。
- 数据库为空时页面展示空状态。
- 网络或权限失败时页面展示错误状态，并允许重新加载。

### 6.4 数据导入流程

v1 不建设后台导入界面，但必须有清晰的人工导入流程。

流程：

1. 使用本地图片分类工具完成 89 张图片标注。
2. 导出 `export/cases.json` 和 `export/optimized-images/`。
3. 将压缩图片上传至微信云存储。
4. 获取每张图片的 `fileID`。
5. 将 `imageFileID` 回填到 `cases.json`。
6. 将最终 `cases.json` 导入云数据库 `cases` 集合。
7. 在小程序端检查图片展示和筛选结果。

验收标准：

- 每条上线案例都有可访问的 `imageFileID`。
- 每条上线案例至少有 `wineType` 和 `packageTypes`。
- 导入后小程序端不依赖本地文件名展示图片。

## 7. 数据结构

案例数据沿用本地分类工具导出的结构。

```json
{
  "id": "case_001",
  "title": "",
  "originalFileName": "IMG_0001.png",
  "uploadFileName": "case_001.jpg",
  "wineType": "白酒",
  "packageTypes": ["礼盒"],
  "styles": ["高端", "新中式"],
  "priceLevel": "高端",
  "crafts": ["烫金"],
  "scenes": ["送礼"],
  "statuses": ["推荐"],
  "keywords": ["白酒", "礼盒", "高端", "新中式", "烫金", "送礼", "推荐"],
  "notes": "",
  "width": 1600,
  "height": 1200,
  "aspectRatio": 1.3333,
  "originalSizeKB": 8300,
  "optimizedSizeKB": 650,
  "imageFileID": "cloud://...",
  "isVisible": true,
  "sortOrder": 1,
  "needsReview": false
}
```

### 7.1 字段说明

- `id`：稳定案例编号，用于展示、排序和排查。
- `title`：可选标题，为空时前端使用分类组合兜底。
- `uploadFileName`：上传前的压缩图片文件名。
- `wineType`：酒类，v1 仅白酒。
- `packageTypes`：包装内容，必填，多选。
- `styles`：风格，多选。
- `priceLevel`：价位感，单选。
- `crafts`：工艺，多选。
- `scenes`：使用场景，多选。
- `statuses`：运营状态，多选。
- `keywords`：由分类字段生成，用于后续搜索扩展。
- `imageFileID`：微信云存储文件 ID，v1 展示图片的关键字段。
- `isVisible`：是否在小程序展示。
- `sortOrder`：展示排序。
- `needsReview`：图片体积或数据质量需要复查。

## 8. v1 页面体验要求

### 8.1 首页体验

首页不是营销落地页，应直接进入案例浏览体验。首屏要让客户立即理解这是酒包装案例库，并看到可筛选的案例。

页面应包含：

- 简洁标题，例如“酒包装案例库”。
- 简短说明，例如“按包装内容、风格和使用场景筛选参考图”。
- 筛选区域。
- 案例图片网格。

### 8.2 视觉方向

界面应偏案例展示和商务沟通工具，不要做成复杂后台。

建议：

- 图片优先，标签辅助。
- 色彩克制，适合白酒包装和商务定制场景。
- 筛选按钮要清晰可点，移动端间距充足。
- 卡片信息不要遮挡图片主体。

## 9. 非功能需求

### 9.1 性能

- 首页首屏应尽快展示加载状态。
- 案例图片使用压缩后的 JPG。
- 图片最长边已经由本地工具压缩至 1600px，v1 不再在小程序端做二次压缩。

### 9.2 可靠性

- 小程序必须处理云环境未配置、数据库为空、图片 fileID 无效等异常。
- 单个图片失败不应影响其他案例展示。

### 9.3 合规和发布

项目上线前需要完成微信小程序相关备案准备。当前项目资料中已保存微信备案操作指引截图，发布计划应预留备案、主体材料、负责人核验、互联网信息服务承诺书等事项。

### 9.4 数据安全

v1 不涉及客户登录、客户上传、订单、手机号、支付等敏感能力。案例图片应确认拥有展示权，避免上传不适合公开展示的客户定制内容。

## 10. 版本规划

### v0：数据准备工具

状态：已实现。

目标：把本地案例图片整理成压缩图片和结构化 JSON。

剩余工作：

- 完成 89 张图片标注。
- 导出图片和 `cases.json`。
- 上传云存储并回填 `imageFileID`。
- 导入云数据库。

### v1：案例展示和筛选小程序

状态：待开发。

范围：

- 替换 quickstart 首页。
- 配置云开发环境。
- 读取 `cases` 集合。
- 展示案例图片网格。
- 支持包装内容、风格、使用场景筛选。
- 支持加载、空状态、错误状态。

### v2：搜索、详情页和收藏/参考图

范围：

- 关键词搜索。
- 案例详情页。
- 客户收藏或勾选参考图。
- 一键复制/分享参考图编号给商家。

### v3：电脑端商家上传和编辑

范围：

- 商家在电脑端上传图片。
- 编辑分类。
- 管理上下架和排序。
- 替代人工导入流程。

### v4：多图需求描述生成

范围：

- 客户选择多张参考图。
- 系统生成需求描述草稿。
- 辅助商家理解客户的偏好组合。

### v5：多商家和权限

范围：

- 多店铺/多商家。
- 权限管理。
- 商家独立案例库。

## 11. 验收清单

### 数据准备验收

- 89 张图片全部进入本地分类工具。
- 所有未跳过案例都有 `wineType` 和 `packageTypes`。
- 导出结果包含 `cases.json` 和 `optimized-images/`。
- 导出的案例 ID 唯一。
- 图片文件名与 `uploadFileName` 对应。
- 上线数据的 `imageFileID` 不为空。

### 小程序 v1 验收

- 微信开发者工具中可以正常打开首页。
- 首页不再展示云开发 quickstart 内容。
- 小程序可以读取云数据库 `cases` 集合。
- 默认展示全部可见案例。
- 包装内容筛选可用。
- 风格筛选可用。
- 使用场景筛选可用。
- 清空筛选可用。
- 空状态、加载状态、错误状态可见且文案清楚。
- 图片加载失败时页面仍可继续浏览其他案例。

### 工程验收

- 本地分类工具现有测试继续通过。
- 小程序核心筛选逻辑应尽量拆成可测试的纯函数。
- 每次超过 3 个文件的功能改动，应先确认范围和验收标准。

## 12. 风险和依赖

- 第一批 89 张图片是否已经完成分类，决定 v1 能否真实演示。
- 微信云开发环境 ID 目前为空，需要先配置。
- 云存储 fileID 回填是人工流程，容易出现图片和案例错配。
- 小程序备案可能影响发布时间。
- 部分案例可能涉及客户隐私或未授权展示，需要上线前复查。
- 如果 v1 过早加入后台、AI、统计等能力，会拖慢核心验证。

## 13. 推荐下一步

1. 先用本地分类工具完成 89 张图片标注和导出。
2. 确认微信云开发环境，并创建 `cases` 集合。
3. 设计一个最小可用的小程序首页：筛选区 + 案例网格 + 状态处理。
4. 导入少量样例数据验证展示和筛选，再导入完整 89 条。
5. 准备备案材料和上线前案例授权复查。
