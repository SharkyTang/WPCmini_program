# 定制需求通知与跟进部署说明

本功能包含管理员邮件提醒、小程序红点、需求认领、管理员单向回复、客户“我的需求”、一次性订阅消息，以及历史联系方式类型修复。所有新能力均为加法式实现，现有需求状态、管理员备注和公开消息通知保持兼容。

## 1. 上线前必须准备

- 一个已开启 SMTP 服务的 QQ 或 163 发件邮箱，以及该邮箱生成的授权码。禁止使用登录密码。
- 两位主负责人和一位备用负责人的接收邮箱，三个地址必须格式有效且互不相同。
- 微信公众平台中已添加的“需求回复/服务进度”一次性订阅模板长 ID、字段名和跳转页面。
- `INQUIRY_ADMIN_OPENIDS` 管理员白名单。
- 当前是用户明确授权的临时共享生产模式：开发版、体验版和正式版都连接 `cloud1-d3gznsms746425a42`。开发/体验操作会写入生产，必须按生产变更执行备份、开关核对和受控验收。
- 一份刚完成并校验通过的 `inquiries` 生产备份。

第一版使用 SMTP，不需要自有域名，也不使用腾讯云 SES。授权码、收件邮箱和模板 ID 不得提交到 Git。

当前账号已有的“升级成功通知”（短编号 10103）和“商品上新通知”（短编号 1330）都不适用于需求回复：业务语义和字段均不匹配，禁止为省事复用。应在微信公众平台新增“咨询回复通知”“服务进度通知”或“工单处理进度通知”一类的一次性订阅模板，并记录“我的模板”中生成的长 `priTmplId` 及其真实字段名；短模板编号不能作为发送接口的模板 ID。

## 2. 集合、权限与索引

在当前明确的目标生产环境中创建以下集合；执行前必须完成并校验备份：

- `inquiry_messages`
- `inquiry_alert_jobs`
- `inquiry_reply_subscriptions`
- `inquiry_admin_events`

四个新增集合和现有 `inquiries` 集合的小程序端直接读写权限均设为 `false`，客户和管理员只能通过云函数访问。规则样例位于 `miniprogram/cloudbase/*.rules.json`，索引清单位于 `miniprogram/cloudbase/inquiry-followup.indexes.json`。

管理端新列表使用 `createdAt + _id` 游标，状态、认领人和经过转义的关键词正则条件均由数据库执行，不再把最近若干条读入云函数后搜索。正则搜索无法利用索引加速，因此关键词限制为 80 字；排序与常用筛选仍必须按清单创建组合索引。

索引清单分别覆盖：无筛选游标、状态筛选游标、规范 `claimedByOpenid` 的“我跟进”游标、状态与“我跟进”的组合，以及同时兼容 `claimedByOpenid/claimedBy` 旧字段的“未认领/我跟进”游标（含状态组合）。发布游标版管理页前必须确认这些索引均已建成，不能用旧的 `claimedBy + status + updatedAt` 索引替代 `createdAt + _id` 稳定排序索引。

部署前逐一应用并复核规则，尤其确认 `inquiries` 同时禁止客户端直接读取和写入。客户身份由 `userData` 的微信上下文 OPENID 决定；管理员身份由 `inquiryAdmin` 的白名单决定。

云函数权限控制必须先从目标 CloudBase 环境导出现有整份规则，再把 `miniprogram/cloudbase/inquiryNotifier.function-rule-merge.json` 中的 `inquiryNotifier: { invoke: false }` 合并进去。该文件只是合并片段，禁止整份覆盖线上规则，也不得改动线上原有的 `*` 通配规则和其他函数条目。该限制不影响定时触发器，也不影响 `userData` 的服务端函数调用；合并后需在“云函数 → 权限控制”中重新读取并复核。

## 3. 云函数环境变量

### `userData`

```text
INQUIRY_FOLLOWUP_ENABLED=false
INQUIRY_EMAIL_ALERTS_ENABLED=false
INQUIRY_CUSTOMER_PUSH_ENABLED=false
INQUIRY_ADMIN_OPENIDS=<与 inquiryAdmin 相同的管理员 OPENID 白名单>
INQUIRY_NOTIFIER_INTERNAL_TOKEN=<随机生成且仅存在于云函数配置中的共享令牌>
INQUIRY_ALERT_RATE_LIMIT_MAX=3
INQUIRY_ALERT_RATE_LIMIT_WINDOW_MINUTES=10
INQUIRY_REPLY_TEMPLATE_ID=
INQUIRY_REPLY_TEMPLATE_FIELDS=title=thing1,time=time2,content=thing3
```

`userData` 在需求写库后 best-effort 调用 `inquiryNotifier`。调用失败只返回延迟状态，不能回滚需求。内部调用必须携带 `INQUIRY_NOTIFIER_INTERNAL_TOKEN`；令牌缺失时 `userData` 不发起调用，且不得把令牌写入响应或日志。`userData`、`inquiryAdmin`、`inquiryNotifier` 三个函数必须配置同一个高熵令牌。

默认同一服务端 OPENID 在连续 10 分钟内只为前三条需求启动邮件提醒链；第四条及以后仍完整写入 `inquiries`、保持管理员待回复红点，只把 `alertTaskStatus` 标为 `suppressed` 并记录固定的安全原因，不创建邮件任务。频控查询使用现有 `openid + createdAt` 索引。这里是防刷软限制：近期计数与需求新增不是一个可串行化的原子操作，因此多个完全并发的请求最多可能按并发数短暂越过阈值；若以后需要严格上限，应另建按 OPENID 哈希分桶的原子计数器，不能靠客户端节流代替。

客户端只有在模板 ID 和字段映射语法合法时才显示订阅按钮，因此该字段配置必须与 `inquiryAdmin` 保持一致。部署配置优先使用单行 compact 格式 `title=thing1,time=time2,content=thing3`，避免 CLI 把 JSON 外观的环境变量解析成对象；代码仍兼容原有 JSON 字符串格式。开启客户推送前还必须调用 `verifySubscriptionTemplates`，确认 `templates.inquiry_reply.usable=true`；该检查会用当前真实 AppID 的“我的模板”列表核对长模板 ID，并确认每个配置字段都存在于模板内容或字段定义中，响应只返回计数、状态码、标题等安全诊断，不返回模板正文或示例。`userData/config.json` 必须授予 `subscribeMessage.getTemplateList`，否则校验会返回 `-604101`。`INQUIRY_ADMIN_OPENIDS` 也要同步配置，否则管理员个人中心的待回复红点为 0。红点按“状态不是 `done/invalid` 且尚无客户可见回复”统计，认领或改为 `contacted/processing` 不会让提醒提前消失。

### `inquiryAdmin`

```text
INQUIRY_ADMIN_OPENIDS=<逗号分隔的管理员 OPENID>
INQUIRY_FOLLOWUP_ENABLED=false
INQUIRY_EMAIL_ALERTS_ENABLED=false
INQUIRY_CUSTOMER_PUSH_ENABLED=false
INQUIRY_NOTIFIER_INTERNAL_TOKEN=<与 userData 完全一致的共享令牌>
INQUIRY_REPLY_TEMPLATE_ID=
INQUIRY_REPLY_TEMPLATE_FIELDS=title=thing1,time=time2,content=thing3
SUBSCRIBE_MESSAGE_STATE=trial
```

正式版上线时将 `SUBSCRIBE_MESSAGE_STATE` 改为 `formal`。字段映射必须和微信公众平台实际模板一致；部署时推荐使用上述 compact 格式，原有 JSON 字符串仍兼容。不一致时站内回复仍保存，但微信提醒保持禁用。

### `inquiryNotifier`

```text
INQUIRY_EMAIL_ALERTS_ENABLED=false
INQUIRY_NOTIFIER_INTERNAL_TOKEN=<与 userData 完全一致的共享令牌>
INQUIRY_SMTP_HOST=smtp.qq.com
INQUIRY_SMTP_PORT=465
INQUIRY_SMTP_SECURE=true
INQUIRY_SMTP_USER=<发件邮箱>
INQUIRY_SMTP_PASS=<SMTP授权码>
INQUIRY_SMTP_FROM=<发件邮箱>
INQUIRY_NOTIFY_PRIMARY_EMAIL=<第一主负责人收件邮箱>
INQUIRY_NOTIFY_PRIMARY_EMAIL_2=<第二主负责人收件邮箱>
INQUIRY_NOTIFY_BACKUP_EMAIL=<备用负责人收件邮箱>
INQUIRY_SMTP_CONNECTION_TIMEOUT_MS=10000
INQUIRY_SMTP_GREETING_TIMEOUT_MS=10000
INQUIRY_SMTP_SOCKET_TIMEOUT_MS=15000
```

三个收件地址均为必填；任一缺失、格式错误或两两重复时，`health` 会返回 `recipient_not_configured`，邮件服务保持禁用。每个收件人使用独立任务和单收件人 SMTP 投递，禁止将多个邮箱拼接到同一个配置值。

如果改用 163，只替换 SMTP 主机和账号配置，不修改代码。函数日志不得打印内部调用令牌、邮件正文、地址、授权码、客户联系方式或 SMTP 原始响应。

SMTP 授权码和收件地址不得写入仓库 `cloudbaserc.json`。当前使用的 CloudBase CLI 3.7.0 在云函数配置更新路径中不会展开 `${ENV_NAME}` 或 `@文件路径`，这两种写法会被原样写入云端。应使用云开发控制台，或使用权限为 `600`、包含已解析实际值的临时配置文件执行合并更新；更新后立即删除临时文件，并重新回拉线上配置，只输出“字段存在/开关状态/收件人数”等脱敏核对结果。

`inquiryNotifier` 必须把函数执行超时设置为 60 秒；普通事件函数的默认超时不足以覆盖数据库任务创建和 SMTP 网络等待。仓库 `cloudbaserc.json` 固定了该值，并把默认 `envId` 锁定为预发环境，避免普通 CLI 操作误触生产。生产部署必须显式指定并二次确认生产环境，不能临时修改这个默认值后遗留在工作树。一分钟定时触发器的 `Message` 也必须设为同一个 `INQUIRY_NOTIFIER_INTERNAL_TOKEN`；否则定时补偿会在任何数据库或 SMTP 操作前被拒绝。

`inquiryAdmin` 的执行超时必须设置为至少 15 秒。管理员概览会并行读取多项计数，首次回复还包含事务、停止邮件任务和可选的订阅消息发送；3 秒配置可能出现回复已经落库但客户端收到超时。生产必须在部署后回读超时值；恢复环境隔离后，预发也要单独回读。

先用 `tcb fn detail inquiryNotifier --json` 回读目标环境，再通过仅存在于 `/private/tmp`、权限为 `600` 且显式含目标 `envId` 的临时配置更新超时：

```bash
tcb --env-id <明确目标环境ID> --config-file /private/tmp/inquiry-notifier-config.json \
  config update fn inquiryNotifier --timeout 60
```

临时配置必须保留线上回读的运行时、入口、内存、依赖安装方式和全部环境变量；完成后立即删除。只更新代码时优先使用 `tcb fn code update`，避免覆盖函数配置。

若目标微信云开发环境不能由当前 CloudBase CLI 账号管理，则在云开发控制台的函数配置中手工设为 60 秒。无论采用哪种方式，都必须重新读取线上配置确认超时值；只运行 `miniprogram/uploadCloudFunction.sh` 不会修改超时设置。

## 4. 部署和灰度顺序

1. 在任何开发版或体验版操作前，先完成生产 `inquiries` 及新增私有集合的备份与可恢复性校验，并核对三组功能开关。
2. 在生产环境创建集合、规则和索引；部署 `inquiryNotifier`，保持邮件开关关闭，确认执行超时为 60 秒、一分钟定时触发器存在，并确认客户端调用规则已合并为 `invoke: false`。
3. 向生产部署向后兼容的 `userData` 和 `inquiryAdmin`。
   - 确认 `userData/config.json` 已授予 `subscribeMessage.getTemplateList` 云调用权限。
   - 确认 `inquiryAdmin/config.json` 已授予 `subscribeMessage.send` 云调用权限。
   - 权限配置必须通过微信开发者工具完整上传对应单个函数；普通 `tcb fn code update` 不会同步 `config.json`。上传后允许微信侧权限缓存刷新，再执行真实云调用验收。
4. 上传开发版/体验版；两者当前都连接真实生产库，只能使用受控账号和明确标记的测试记录。
5. 在确认邮件与客户推送开关为关闭后，运行微信号、手机号、邮箱三条受控提交探针；检查生产数据库字段、后台标签和历史功能。
6. 需要验证邮件时，只在已核对的受控收件人范围内临时开启生产邮件开关；验证两位主负责人立即邮件、备用负责人 5 分钟邮件、三人 15 分钟升级邮件，以及认领/首次回复后停止提醒。验收后立即恢复原开关状态。
7. 用 `verifySubscriptionTemplates` 核对 `templates.inquiry_reply.usable=true` 后再开启客户推送，只用已知情的测试账号验证接受、拒绝、禁用、消费一次和深链跳转。
8. 将生产配置重新读回作为发布门禁：核对集合、索引、deny 规则、整份函数权限规则、Node.js 运行时、60 秒超时、定时器、三组功能开关和白名单；确认 `userData` 与 `inquiryAdmin` 的模板 ID/字段映射逐字一致，且 SMTP 授权码只能确认“已配置”而不能打印其值。
9. 完成真实云端依赖安装、`health` 探针和 SMTP 受控收件测试。当前没有独立预发缓冲，任何失败都必须先关闭对应开关并停止继续试错；不得把临时共享模式当成绕过生产门禁的理由。
10. 上传并发布正式版，再依次开启：`INQUIRY_FOLLOWUP_ENABLED`、`INQUIRY_EMAIL_ALERTS_ENABLED`、`INQUIRY_CUSTOMER_PUSH_ENABLED`；每开一项都重读配置并执行对应探针。
11. 观察至少 24 小时；异常时关闭对应开关，不删除新增集合或回复数据。
12. 临时验收阶段结束后，在日常开发恢复前把 `develop` / `trial` 重新映射到独立预发环境，并重新跑一次环境路由测试。

## 5. 历史联系方式修复

先按 `docs/需求联系方式历史数据迁移说明.md` 运行 dry-run。正式写入必须提供已校验备份、目标环境双重确认和显式报告路径。迁移规则为邮箱、手机号严格推断，其余非空值标记为 `wechat + inferred_legacy`；管理员界面会显示“旧数据推断，待确认”，可以人工修正。

## 6. 验收与故障处理

- SMTP 正常时，提交至服务器受理邮件 P95 不超过 60 秒；最终收件箱投递受邮箱服务商影响。
- 邮件错误不影响需求入库和管理员红点。
- 同一 OPENID 在频控窗口内的第四条需求仍可在管理端查看并保留待回复红点，但不会触发新的邮件链。
- 管理员红点在认领、改为已联系或跟进中后仍保留，只有首次客户可见回复或状态改为已完成/无效后才移除。
- 网络超时标记为结果未知，不立即重发同一阶段；5/15 分钟升级仍继续。
- 新需求、回复和订阅信息不进入公开的 `app_notifications`。
- 客户只能读取自己 OPENID 对应的需求，响应中不包含管理员备注、管理员 OPENID、提醒任务或审计事件。
- 回归命令为 `npm test`，并对三个新云函数执行 `node --check`。真机验收至少覆盖 iOS、Android、两个客户账号、两名管理员和一个非管理员账号。
